# DeskHub — платформа бронирования мест в коворкингах

## Стек
- Python 3.x, Django
- SQLite (dev)
- Gunicorn + Nginx (prod)

## Локальный запуск

1. Клонировать репозиторий и перейти в папку проекта.
2. Создать и активировать виртуальное окружение:
```bash
   python -m venv venv
   source venv/bin/activate  # Windows: venv\Scripts\activate
```
3. Установить зависимости:
```bash
   pip install -r requirements.txt
```
4. Скопировать `.env.example` в `.env` и заполнить значения:
```bash
   cp .env.example .env
```
5. Применить миграции:
```bash
   python manage.py migrate
```
6. Создать суперпользователя (для доступа к админке):
```bash
   python manage.py createsuperuser
```
7. Сгенерировать слоты на ближайшие дни (см. раздел ниже):
```bash
   python manage.py generate_slots --days 30
```
8. Запустить сервер разработки:
```bash
   python manage.py runserver
```
9. Открыть http://127.0.0.1:8000/

## Переменные окружения

Конфигурация читается из `.env` через `python-dotenv` + `os.getenv`.
См. `.env.example` — обязательные переменные:

| Переменная      | Описание                                              |
|-----------------|--------------------------------------------------------|
| `SECRET_KEY`    | Секретный ключ Django. Обязателен, сервер не запустится без него |
| `DEBUG`         | `True`/`False`. На проде — всегда `False`              |
| `ALLOWED_HOSTS`  | Список доменов/IP через запятую                       |
| `TIME_ZONE`     | Часовой пояс сервера по умолчанию (не путать с часовым поясом городов — см. ARCHITECTURE.md) |
| `RESERVATION_RESPONSE_DEADLINE_HOURS` | Часов до автоотмены заявки, на которую не ответил менеджер (по умолчанию 12) |

## Роли пользователей

- **Гость** — просмотр коворкингов, фильтрация, добавление слотов в корзину (корзина хранится в сессии, авторизация не требуется).
- **Авторизованный пользователь** — оформление брони, личный кабинет с историей заявок и отменой.
- **Staff (менеджер)** — управление городами/коворкингами/местами/слотами/заявками через `/admin/`.

## Управление системой (для менеджера/администратора)

Всё управление происходит через `/admin/` — вход туда доступен только
пользователям с `is_staff=True` (создаётся через `createsuperuser` или
через саму админку другим суперпользователем).

### 1. Настройка каталога: город → коворкинг → место

Порядок создания важен — каждая следующая сущность ссылается на предыдущую:

1. **Города** (`/admin/coworkings/city/`) — создать город, указать его
   часовой пояс (`timezone`). Часовой пояс общий для всех коворкингов
   в этом городе (все коворкинги одного города физически находятся
   в одном часовом поясе, поэтому поле хранится здесь, а не на каждом
   коворкинге отдельно).
2. **Коворкинги** (`/admin/coworkings/coworking/`) — привязать к городу,
   указать адрес, рабочие часы (`work_time_start`/`work_time_end`) —
   именно в эти часы позже будут нарезаны слоты.
3. **Места** (`/admin/coworkings/place/`) — привязать к коворкингу, указать
   тип (`Workplace`/`Meeting_room`), вместимость (`capacity`). Поле
   `is_active` позволяет временно скрыть место с сайта без удаления
   (например, место на ремонте) — такое место не будет отображаться
   в списках и не будет участвовать в генерации новых слотов.

### 2. Генерация слотов

Слоты не создаются автоматически при создании места — их нужно сгенерировать
отдельной командой. Команда нарезает рабочий день каждого активного места
на часовые интервалы, на N дней вперёд от сегодняшнего дня (по местному
времени города, в котором находится коворкинг).

```bash
python manage.py generate_slots --days 30
```

- `--days` — на сколько дней вперёд генерировать (по умолчанию 30).
- Команда безопасна для повторного запуска: уже существующие слоты не
  дублируются, создаются только недостающие.
- Рекомендуется запускать регулярно (например, раз в неделю через cron),
  чтобы горизонт доступных дат на сайте не "заканчивался":
### пример строки crontab — каждый понедельник в 03:00

0 3 * * 1 cd /path/to/project && /path/to/venv/bin/python manage.py generate_slots --days 30


### 3. Автоматическая обработка просроченных заявок

Команда `process_reservations` отменяет заявки, на которые менеджер не
ответил в течение `RESERVATION_RESPONSE_DEADLINE_HOURS` часов (по умолчанию
12, настраивается в `.env`), и переводит завершившиеся подтверждённые брони
в статус «Завершена».

```bash
python manage.py process_reservations
```

Рекомендуется запускать регулярно через cron, например каждые 10 минут:

## crontab -e

*/10 * * * * cd /path/to/project && /path/to/venv/bin/python manage.py process_reservations >> /path/to/project/logs/cron.log 2>&1


### 4. Обработка заявок на бронирование

Заявки видны в `/admin/reservations/reservation/`. У каждой заявки есть
статус: «Ожидает» → «Подтверждена» / «Отклонена» → (при необходимости)
«Отменена» / «Завершена».

**Подтвердить/отклонить одну заявку:** открыть заявку, изменить поле
`status`, сохранить.

**Массовая обработка:** выбрать несколько заявок чекбоксами в списке,
в выпадающем списке действий сверху выбрать «Подтвердить выбранные заявки»
или «Отклонить выбранные заявки», нажать «Выполнить».

⚠️ **Не редактировать статус через быстрое редактирование в списке**
(`list_editable`) — статус должен меняться только через форму заявки или
через bulk-действия выше. Это гарантирует, что связанный слот корректно
освобождается или занимается вместе со сменой статуса (см. ARCHITECTURE.md,
раздел «Занятость слота»).

Быстрый доступ к заявкам, ожидающим рассмотрения, есть прямо в шапке
сайта для сотрудников — пункт меню «Управление заявками» (виден только
при `is_staff=True`).

### 5. Просмотр логов запросов

Логи всех запросов пишутся в `logs/requests.log` (создаётся автоматически
при старте сервера). Формат строки:

дата время УРОВЕНЬ метод путь -> статус [время выполнения мс] user=...
