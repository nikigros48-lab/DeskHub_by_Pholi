# DeskHub — платформа бронирования мест в коворкингах

Сайт, на котором можно найти коворкинг в своём городе, выбрать рабочее место
или переговорную, добавить свободные часовые слоты в корзину и отправить заявку
на бронирование. Менеджер подтверждает или отклоняет заявки через админку.

## Стек

- Python 3.14, Django 6.1
- PostgreSQL 18 (Docker Compose)
- django-environ (конфигурация из `.env`)
- pytest, pytest-django, freezegun (тесты)
- Gunicorn + Nginx (прод)

## Продакшен-окружение

- Домен: https://deskhub-by-pholi.ru
- Хостинг: REG.RU, облачный VPS (Рег.облако), Москва
- ОС: Ubuntu 24.04 LTS
- Стек: Nginx (reverse proxy + статика) + Gunicorn (3 workers) + Django + PostgreSQL

## Локальный запуск

1. Клонировать репозиторий и перейти в папку проекта.
2. Создать и активировать виртуальное окружение:
   ```bash
   python -m venv .venv
   source .venv/bin/activate   # Windows: .venv\Scripts\activate
   ```
3. Установить зависимости:
   ```bash
   pip install -r requirements.txt
   ```
4. Скопировать `.env.example` в `.env` и заполнить значения (см. таблицу ниже):
   ```bash
   cp .env.example .env
   ```
5. Поднять PostgreSQL в Docker (параметры берутся из `DB_*` в `.env`):
   ```bash
   docker compose up -d
   ```
6. Применить миграции и создать суперпользователя:
   ```bash
   python manage.py migrate
   python manage.py createsuperuser
   ```
7. Сгенерировать слоты на ближайшие дни (после создания городов, коворкингов и мест в админке):
   ```bash
   python manage.py generate_slots --days 30
   ```
8. Запустить сервер разработки:
   ```bash
   python manage.py runserver
   ```
9. Открыть http://127.0.0.1:8000/

## Переменные окружения

Конфигурация читается из `.env` через `django-environ`. Шаблон — `.env.example`.

| Переменная | Описание |
|------------|----------|
| `SECRET_KEY` | Секретный ключ Django. Обязателен: без него сервер не запустится |
| `DEBUG` | `True`/`False`. На проде всегда `False` |
| `ALLOWED_HOSTS` | Список доменов/IP через запятую |
| `TIME_ZONE` | Часовой пояс сервера по умолчанию (по умолчанию `Asia/Novosibirsk`). Не путать с часовыми поясами городов, см. `ARCHITECTURE.md` |
| `RESERVATION_RESPONSE_DEADLINE_HOURS` | Часов до автоотмены заявки, на которую не ответил менеджер (по умолчанию 12) |
| `DB_NAME`, `DB_USER`, `DB_PASSWORD` | Параметры PostgreSQL. Те же значения использует `docker-compose.yml` |
| `DB_HOST`, `DB_PORT` | Адрес БД (по умолчанию `localhost` и `5432`) |

`.env` в репозиторий не попадает (`.gitignore`), в репозитории лежит только `.env.example`.

## Тесты

```bash
pytest          # весь набор
pytest -rx      # плюс список известных багов (xfail), если они есть
pytest apps/coworkings/tests/test_filters.py   # один файл
```

Для тестов нужна запущенная БД (`docker compose up -d`): `pytest-django` сам создаёт
и удаляет отдельную базу `test_<DB_NAME>`, рабочие данные не затрагиваются.

### Что покрыто

| Область | Что проверяется |
|---------|-----------------|
| Список коворкингов (`CoworkingListView`) | фильтры по городу, типу места и дате (по отдельности и в комбинациях), сессия, `distinct`, занятые и прошедшие слоты, граница «слот начинается ровно сейчас», часовые пояса разных городов, битые значения в сессии |
| Форма фильтров и сброс | запись фильтров в сессию, предзаполнение, невалидные данные, доступ только для авторизованных, `clear_filters` (только POST), сквозной сценарий «фильтр → список» |
| Места | список мест коворкинга, порядок, детальная страница, свободные слоты на дату, дата по умолчанию в часовом поясе коворкинга |
| JSON API коворкингов | формат ответов, фильтры, коды 400/404/405, время слотов, часовые пояса |
| Пользователи | регистрация, вход/выход, профиль, валидация полей |
| Информационные страницы | рендер шаблонов |

### Что не покрыто

Корзина, бронирования (`reservations`), management-команды (`generate_slots`,
`process_reservations`) и API статуса брони. Это следующий шаг.

### Устройство тестов

- `conftest.py` в корне: `make_user`, `auth_client`, `set_session`.
- `apps/coworkings/tests/conftest.py`: фабрики `make_city`, `make_coworking`, `make_place`,
  `make_slot` с уникальными значениями по умолчанию, сценарий `two_cities`,
  фикстура `url` (короткие алиасы маршрутов) и `frozen_now` (замороженное время через `freezegun`).
- Даты в тестах считаются от сегодняшней, без жёстко прописанных чисел.

## Роли пользователей

- **Гость**: просмотр коворкингов и мест, добавление слотов в корзину
  (корзина хранится в сессии, авторизация не нужна).
- **Авторизованный пользователь**: настройка фильтров, оформление брони, личный кабинет
  с историей заявок и отменой.
- **Staff (менеджер)**: управление городами, коворкингами, местами, слотами и заявками через `/admin/`.

## Управление системой (для менеджера/администратора)

Всё управление идёт через `/admin/`. Вход доступен только пользователям с `is_staff=True`
(создаются через `createsuperuser` или через саму админку).

### 1. Настройка каталога: город → коворкинг → место

Порядок важен: каждая следующая сущность ссылается на предыдущую.

1. **Города** (`/admin/coworkings/city/`): название и часовой пояс (`timezone`).
   Пояс общий для всех коворкингов города, поэтому хранится здесь, а не на коворкинге.
2. **Коворкинги** (`/admin/coworkings/coworking/`): город, адрес, рабочие часы
   (`work_time_start`/`work_time_end`). В эти часы нарезаются слоты.
3. **Места** (`/admin/coworkings/place/`): коворкинг, тип (`Workplace`/`Meeting_room`),
   вместимость. Флаг `is_active` скрывает место с сайта без удаления: оно не показывается
   в списках, не учитывается в фильтрах и не получает новых слотов.

### 2. Генерация слотов

Слоты не создаются автоматически при создании места. Команда нарезает рабочий день
каждого активного места на часовые интервалы на N дней вперёд от сегодняшней даты
(по местному времени города коворкинга).

```bash
python manage.py generate_slots --days 30
```

- `--days`: на сколько дней вперёд генерировать (по умолчанию 30).
- Команда безопасна для повторного запуска: существующие слоты не дублируются.
- Рекомендуется запускать регулярно через cron, чтобы горизонт дат не «заканчивался».

Пример crontab (каждый понедельник в 03:00):

```cron
0 3 * * 1 cd /path/to/project && /path/to/venv/bin/python manage.py generate_slots --days 30
```

### 3. Автоматическая обработка заявок

Команда `process_reservations` отменяет заявки, на которые менеджер не ответил
в течение `RESERVATION_RESPONSE_DEADLINE_HOURS`, и переводит завершившиеся
подтверждённые брони в статус «Завершена».

```bash
python manage.py process_reservations
```

Пример crontab (каждые 10 минут):

```cron
*/10 * * * * cd /path/to/project && /path/to/venv/bin/python manage.py process_reservations >> /path/to/project/logs/cron.log 2>&1
```

### 4. Обработка заявок на бронирование

Заявки видны в `/admin/reservations/reservation/`. Статусы:
«Ожидает» → «Подтверждена» / «Отклонена» → (при необходимости) «Отменена» / «Завершена».

- **Одна заявка:** открыть, изменить `status`, сохранить.
- **Массово:** выбрать заявки чекбоксами и применить действие «Подтвердить выбранные заявки»,
  «Отклонить выбранные заявки» или «Отметить как завершённые».

Не меняйте статус через `list_editable` и не делайте массовых `QuerySet.update()`:
синхронизация занятости слота живёт в `Reservation.save()` (см. `ARCHITECTURE.md`).

В шапке сайта для сотрудников есть пункт «Управление заявками» (виден при `is_staff=True`):
он ведёт на список заявок со статусом «Ожидает».

### 5. Логи запросов

Каждый запрос пишется в `logs/requests.log` (создаётся автоматически) и в консоль.
Формат строки:

```
дата время УРОВЕНЬ метод путь -> статус [время мс] user=...
```
