# Архитектура DeskHub

## Приложения (apps)

- **info** — статические информационные страницы (главная, о нас, контакты).
- **users** — кастомная модель пользователя (`AUTH_USER_MODEL`), регистрация, профиль.
- **coworkings** — города, коворкинги, места (`Place`), слоты (`Slot`).
- **reservations** — брони (`Reservation`), их статусы, оформление и отмена.
- **cart** — корзина слотов на основе сессии Django (доступна гостям).

Каждое приложение, где это уместно, содержит подпакет `api/` со своими
`views.py`/`urls.py` — см. раздел «API» ниже.

## Ключевые модели и их связи

City 1--* Coworking 1--* Place 1--* Slot *--1 Reservation *--1 User


`City` хранит поле `timezone`: все коворкинги одного города физически
находятся в одном часовом поясе, поэтому это свойство города, а не
каждого коворкинга отдельно — иначе два коворкинга одного города могли бы
теоретически иметь рассинхронизированные значения без всякого смысла.

## Хранение времени

`USE_TZ = False`. Время в `Slot.time_start`/`time_end` хранится как
"наивное" локальное время города, в котором находится коворкинг места
(`place.coworking.city.timezone`), а не время сервера и не UTC.
Конвертация в `now()` конкретного города делается через
`ZoneInfo(city.timezone)` во всех местах, где нужно сравнить с текущим
временем (фильтрация будущих слотов, генерация слотов).

## `CustomQSMixin`

Вспомогательный миксин в `coworkings/views.py`, добавляющий
`select_related()` к queryset вьюхи. Список полей задаётся атрибутом
`select_related_fields` в наследнике, т.к. путь до `City` различается
в зависимости от модели, на которой строится вьюха:
- у `Coworking` это `"city"` (прямой FK);
- у `Place` — `"coworking__city"` (через промежуточную связь).

Миксин объявляется **первым** среди родительских классов
(`class X(CustomQSMixin, ListView)`, не наоборот) — иначе Django CBV
не вызовет `super().get_queryset()` в сторону миксина, и `select_related`
не применится.

## Занятость слота: два синхронизированных состояния

- `Slot.user` — быстрый признак "слот занят/свободен" для выборок.
- `Reservation.status` — источник истины о том, почему слот занят.

Синхронизация происходит в `Reservation.save()`: при переходе статуса
в `awaiting`/`approved` слот занимается, при переходе из них — освобождается.

**Важно:** массовое изменение статуса через `QuerySet.update()` (в том
числе через `list_editable` в админке) обходит эту синхронизацию —
поэтому в `ReservationAdmin` статус меняется только через `actions`,
вызывающие `.save()` на каждом объекте.

## Автоматический жизненный цикл заявок

Раз в N минут (см. README.md, раздел «Cron-задачи») запускается команда
`process_reservations`, которая обрабатывает два случая:

1. **Просроченные заявки** — если заявка в статусе `awaiting` дольше
   `RESERVATION_RESPONSE_DEADLINE_HOURS` часов (настраивается через `.env`,
   по умолчанию 12), она автоматически переводится в `cancelled`.
   Сравнение идёт с серверным временем (`timezone.now()`), т.к. дедлайн
   ответа менеджера — общий бизнес-параметр, не привязанный к конкретному
   городу.

2. **Завершённые брони** — если заявка в статусе `approved`, а время
   окончания слота (`slot.time_end`) уже прошло, она переводится
   в `completed`. Сравнение идёт с местным временем города, в котором
   находится коворкинг слота — не с серверным временем (см. раздел
   «Хранение времени» выше).

В обоих случаях статус меняется через `Reservation.save()` (никогда через
`QuerySet.update()`), чтобы сработала синхронизация занятости слота.

## Корзина

Реализована через `request.session['cart']` — список словарей с данными
слотов. Доступна неавторизованным пользователям. Требование авторизации
появляется только на шаге оформления брони (`CartReservationView`).

При переходе на страницу логина `CartReservationView` явно указывает
`next=/cart/` (через переопределённый `handle_no_permission()`), а не
на себя — иначе после логина пользователя редиректило бы обратно на
POST-only эндпоинт через GET, что даёт `405 Method Not Allowed`.

При оформлении брони используется `select_for_update()` внутри
`transaction.atomic()`, чтобы исключить двойное бронирование одного слота
при параллельных запросах.

## Middleware

- `RequestLoggingMiddleware` (`deskhub/middleware.py`) — логирует
  метод/путь/статус/время выполнения каждого запроса в
  `logs/requests.log` и в консоль.
- `CartCountMiddleware` (`deskhub/middleware.py`) — прокидывает
  `request.cart_count` для отображения количества элементов корзины
  в шапке сайта без обращения к `context_data` каждой отдельной вьюхи.

## API

Реализовано средствами чистого Django (`JsonResponse`), без DRF —
согласно нефункциональному требованию ТЗ.

Логика API распределена по доменным приложениям, а не собрана в одном
общем `apps/api` — со-расположение кода одного домена
(модели + вьюхи + API одного приложения лежат рядом) облегчает
дальнейший рефакторинг и упрощает удаление/выделение модуля целиком:

apps/coworkings/api/ — CoworkingListAPIView, PlaceSlotsAPIView
apps/reservations/api/ — ReservationStatusAPIView


Корневой `deskhub/urls.py` лишь собирает эти под общим префиксом `/api/`
через несколько `include()` на один и тот же путь — сама точка входа для
клиента API остаётся единой, несмотря на то что логика физически
раздроблена по приложениям.

Аутентификация в API-вьюхах проверяется вручную
(`request.user.is_authenticated`) с ответом `401` в JSON, а не через
`LoginRequiredMixin`/`@login_required` — эти механизмы Django рассчитаны
на HTML-редирект на страницу логина, что не подходит для API-клиента,
ожидающего JSON-ответ.

Подробная спецификация эндпоинтов — в `API.md`.

## Конфигурация

Секреты и параметры окружения (`SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`,
`TIME_ZONE`, `RESERVATION_RESPONSE_DEADLINE_HOURS`) читаются из `.env`
через `python-dotenv` + `os.getenv()`, а не хранятся в `settings.py`
напрямую. `.env` исключён из репозитория (`.gitignore`), в репозитории
лежит только `.env.example` с плейсхолдерами.
