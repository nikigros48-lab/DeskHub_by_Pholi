# Архитектура DeskHub

## Приложения (apps)

- **info**: статические страницы (главная, о нас, контакты).
- **users**: кастомная модель пользователя (`AUTH_USER_MODEL = users.User`, поля `phone` и `avatar`),
  регистрация (с автоматическим входом), профиль.
- **coworkings**: города, коворкинги, места (`Place`), слоты (`Slot`), фильтры, JSON API каталога.
- **reservations**: брони (`Reservation`), статусы, оформление из корзины, отмена, JSON API статуса.
- **cart**: корзина слотов в сессии Django (доступна гостям).

Приложения с API содержат подпакет `api/` со своими `views.py` и `urls.py` (см. раздел «API»).

## Ключевые модели и связи

```
City 1--* Coworking 1--* Place 1--* Slot *--0..1 User
                                     |
                                     1--* Reservation *--1 User
```

`Slot.user` пустой, пока слот свободен. `Reservation.slot` может стать `NULL`
(`on_delete=SET_NULL`), если слот удалили.

`City` хранит `timezone`: все коворкинги города физически в одном часовом поясе, поэтому это
свойство города, а не коворкинга. Иначе у двух коворкингов одного города могли бы разойтись значения.

Тип места задан через `Place.PlaceType` (`TextChoices`). В базе, сессии и API хранится значение
(`"Workplace"`, `"Meeting_room"`), в интерфейсе показывается подпись (`label`).

## Хранение времени

`USE_TZ = False`. `Slot.time_start`/`time_end` хранятся как **наивное локальное время города**
коворкинга (`place.coworking.city.timezone`), а не серверное и не UTC. Рабочие часы коворкинга
(`work_time_start`/`work_time_end`) тоже локальные, поэтому `Slot.clean()` сравнивает их напрямую.

Везде, где слот сравнивается с «сейчас», текущее время считается в поясе города:

```python
now_coworking = datetime.now(ZoneInfo(city.timezone)).replace(tzinfo=None)
```

Это применяется в фильтре списка, на странице места, в API, при оформлении брони,
при генерации слотов и при завершении броней. Слот считается доступным, пока
`time_start > now_coworking` (слот, начинающийся ровно сейчас, уже недоступен).

Ограничение: при такой схеме нет защиты от перевода часов. Для городов без перехода
на летнее время (в том числе вся Россия) это не проблема. Если появятся другие города,
придётся перейти на `USE_TZ = True` и хранить время в UTC.

## Фильтры списка коворкингов

Страница фильтров (`CoworkingFilterView`, только для авторизованных) пишет выбор в сессию:

| Ключ сессии | Значение |
|-------------|----------|
| `selected_city` | **название** города (не id) |
| `place_type` | значение `Place.PlaceType` |
| `filter_date` | дата в формате ISO (`YYYY-MM-DD`) |

Пустые значения записываются как `None`. `CoworkingListView` читает эти ключи (гости тоже)
и применяет фильтры. Сброс: `clear_filters` (только POST) удаляет все три ключа.

Семантика:

- **без фильтров** показываются все коворкинги, даже без активных мест;
- **город** фильтрует по названию;
- **тип места** оставляет коворкинги, у которых есть **активное** место этого типа (`distinct()`
  убирает дубли при нескольких местах);
- **дата** оставляет коворкинги, у которых есть свободный (без `user`) слот в активном месте
  на эту дату, ещё не начавшийся по времени города; при заданном типе учитываются только слоты
  мест этого типа;
- некорректная дата в сессии молча игнорируется, фильтр по дате просто не применяется.

Имена ключей контекста шаблона отличаются от ключей сессии (`selected_place_type`,
`selected_date`), см. `CoworkingListView.get_context_data`.

## `CustomQSMixin`

Миксин в `coworkings/views.py`, добавляющий `select_related()` к queryset вью. Поля задаются атрибутом
`select_related_fields`, потому что путь до `City` зависит от модели:

- у `Coworking` это `"city"`;
- у `Place` это `"coworking__city"`.

Миксин объявляется **первым** среди родителей (`class X(CustomQSMixin, ListView)`), иначе
`super().get_queryset()` не дойдёт до него и `select_related` не применится.

## Занятость слота: два синхронизированных состояния

- `Slot.user`: быстрый признак «занят/свободен» для выборок.
- `Reservation.status`: источник истины о том, почему слот занят.

Синхронизация в `Reservation.save()`: при переходе статуса в `awaiting`/`approved` слот занимается,
при переходе из этих статусов в другие (`declined`, `cancelled`, `completed`) освобождается.
Затем вызывается `full_clean()`: он проверяет, что слот не занят другим пользователем
и что `amount_people` не превышает вместимость места.

Массовое изменение статуса через `QuerySet.update()` (в том числе через `list_editable` в админке)
обходит эту синхронизацию, поэтому в `ReservationAdmin` статус меняется только через `actions`,
которые вызывают `.save()` на каждом объекте.

## Автоматический жизненный цикл заявок

Команда `process_reservations` (cron, см. README) обрабатывает два случая:

1. **Просроченные заявки.** Заявка в статусе `awaiting` старше `RESERVATION_RESPONSE_DEADLINE_HOURS`
   (по умолчанию 12) переводится в `cancelled`. Сравнение идёт с серверным `timezone.now()`: дедлайн
   ответа менеджера общий для всех и не привязан к городу.
2. **Завершённые брони.** Заявка `approved`, у которой `slot.time_end` уже прошёл, переводится
   в `completed`. Сравнение идёт с местным временем города слота.

В обоих случаях статус меняется через `Reservation.save()`, а не через `update()`.

## Корзина

Хранится в `request.session["cart"]`: список словарей (`slot_id`, `place_id`, `place_name`, `date`,
`time_start`, `time_end`, `amount_people`). Доступна гостям. При добавлении проверяется,
что слоты свободны и что `amount_people` не превышает вместимость места.

Авторизация нужна только при оформлении (`CartReservationView`). При отсутствии прав
`handle_no_permission()` отправляет на логин с `next=/cart/`, а не на сам POST-эндпоинт: иначе после
входа пользователя вернуло бы на него GET-запросом и вышло бы `405 Method Not Allowed`.

Оформление идёт внутри `transaction.atomic()` с `select_for_update()` по каждому слоту: это
исключает двойное бронирование при параллельных запросах (на PostgreSQL блокировка работает по-настоящему,
на SQLite нет). Если один слот не прошёл проверку (занят, исчез, уже начался), вся транзакция откатывается,
проблемный слот убирается из корзины, пользователю показывается причина.

## Middleware

- `RequestLoggingMiddleware` (`deskhub/middleware.py`): метод, путь, статус и время выполнения
  каждого запроса в `logs/requests.log` (ротация, 5 МБ × 3 файла) и в консоль.
- `CartCountMiddleware`: кладёт `request.cart_count` для счётчика корзины в шапке без правки контекста каждой вью.

## API

Реализовано на чистом Django (`JsonResponse`), без DRF. Код лежит в приложениях по доменам,
а не в общем `apps/api`: модели, вью и API одного домена рядом, модуль проще выделить или удалить.

```
apps/coworkings/api/    CoworkingListAPIView, PlaceSlotsAPIView
apps/reservations/api/  ReservationStatusAPIView
```

Корневой `deskhub/urls.py` подключает оба набора маршрутов под общим префиксом `/api/`
двумя `include()`, поэтому для клиента точка входа одна.

Аутентификация в API проверяется вручную (`request.user.is_authenticated`) с ответом `401` в JSON,
а не через `LoginRequiredMixin`/`@login_required`: они делают HTML-редирект на логин, а API-клиенту нужен JSON.

Разрешён только `GET`, остальные методы дают `405`. Подробности: `API.md`.

## Тесты

Тесты лежат рядом с кодом (`apps/<app>/tests/`), конфигурация в `pytest.ini`.

- Общие фикстуры (`make_user`, `auth_client`, `set_session`) в корневом `conftest.py`.
- Фикстуры каталога в `apps/coworkings/tests/conftest.py`: фабрики с уникальными значениями
  по умолчанию (счётчики), сценарий `two_cities`, алиасы маршрутов (`url`), `frozen_now` и `future_day`.
- Время замораживается через `freezegun`. «Сейчас» это сегодня плюс год, 06:00 UTC
  (13:00 в Новосибирске, 09:00 в Москве), а обычные тесты используют день через 2 дня от сегодняшнего.
  Так результат не зависит от времени запуска, и в тестах нет жёстко прописанных дат.
- Тест на часовые пояса проверяет разные города в один и тот же момент, а тесты границы
  проверяют слоты за минуту до, ровно в момент и после «сейчас».

Нюанс `freezegun`: наивный `datetime.now()` при заморозке равен UTC. Это учтено в тесте,
который проверяет, что дата по умолчанию на странице места считается по поясу коворкинга, а не сервера.

## Известные ограничения

- `PlaceDetailView` не сверяет `coworking_id` из URL с коворкингом места: страница
  `/coworkings/<другой id>/<pk места>/` откроется. Ветка `request.GET["coworking_id"]` в `PlaceListView`
  недостижима, так как параметр всегда приходит из URL.
- API списка коворкингов с фильтром по дате делает по одному запросу на коворкинг (N+1).
  Для текущих объёмов приемлемо, при росте данных заменить одним запросом.
- Нет защиты от перехода на летнее время (см. «Хранение времени»).

## Конфигурация

Секреты и параметры окружения (`SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, `TIME_ZONE`,
`RESERVATION_RESPONSE_DEADLINE_HOURS`, `DB_*`) читаются из `.env` через `django-environ`
и не хранятся в `settings.py`. `.env` исключён из репозитория, в репозитории лежит `.env.example`.
PostgreSQL поднимается через `docker-compose.yml` теми же переменными `DB_*`.
